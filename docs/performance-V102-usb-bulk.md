# V102候補：USBまとめ読み修正後の性能・耐久試験

2026-10-20測定。診断なし通常候補のSHA-256は `f073740c23d2c449a529bcc27037a8723530d11662f99891fa866a034044cf85`。USB入力の読出し単位だけを最大64バイトへ変更した。[原因分析](usb-input-analysis-V102.md)。

## 測定環境と受信側の制約

Mac miniのUSBシリアル→pico-slcan→MCP2518FD SocketCAN。Piの公称サンプル点80%、SJWは125k/500kで8、1Mで4。FDデータ2M・サンプル点80%・SJW2。125kはClassic。各条件3回。速度は対向のハードウェア受信時刻で算出した。

Piの通常受信設定では1Mbps・DLC0の飽和送信で受信不足が生じた。専用kretprobeで、カーネルのCAN RX offloadキュー投入時のENOBUFS 38件が不足38件と一致した。通常設定の未合格試行は保持し、Picoの送信欠落とは判定しない。

以下の48試行は、測定器側rcan2のみをrx-usecs-irq 250µs・rx-frames-irq 8へ設定して実施した。設定要求は250µs/1フレームで、ドライバの読み戻しが8フレームだった。RXリング20/TX4、threaded NAPI 0は維持。全48試行を通してPiのカーネル受信エラー5種類の増分が0だった。終了時は元の0µs/1フレームへ復元した。RTTにはこのPi設定の影響も含む。

通常候補から生成した別の診断ビルドで既存FIFO 1,000枠をRAMから満たし、通常と同じ送信サービスで排出した。通常候補の速度と区別する。

## 通常受信設定の追加比較

先にPiの通常受信設定で実施したデータ付き15試行も全件・内容・順序・バースト・echo照合に合格した。これらを250µs設定の表へ混ぜず、機械可読結果の別グループへ保持した。USB入力修正前の値は[10/19の記録](performance-V102.md)に保持する。

これらはこの環境・供給方式での観測速度であり、全条件の絶対最大速度やリアルタイム遅延保証ではない。ACKが戻らない場合は保持・再送するため、障害時遅延に有限の上限はない。

## 対称24時間試験（ユーザー指示で途中停止）

通常受信設定0µs/1フレームへ戻し、診断なし通常候補で730件/秒ずつを120秒校正した。各87,600件が内容・順序・受付応答まで一致し、要求ペース維持、BEL・ソケットdrop・カーネル受信エラー・不要な復旧は0だった。復旧6条件×10回、通常候補の実bus-off復帰10回、上記48性能試行を監査してから開始した。

## 2026-10-20 09:32 JSTの途中停止

ユーザーの「ここで見つけた不具合対応を織り込む」指示により09:32:22 JSTに停止要求を送った。最後の完全なチェックポイントは1時間29分30.105秒、Pico→Pi 3,920,178件、Pi→Pico 3,920,148件。対向の記録時刻は別であり、集計時点の差は欠落を意味しない。不一致・BEL・ソケットdrop・Piのカーネル受信エラー5種類・不要な復旧はすべて0だった。停止時の最終排出まで照合した件数ではなく、チェックポイントの記録である。

監督・送受信プロセスの終了、通常候補UF2への復元、Pi boot ID不変、rcan2を125k/2M・サンプル点80%・DOWN、受信割り込み0µs/1フレーム、RXリング20/TX4、threaded NAPI 0へ戻したことを確認した。他のCANポートはDOWNを維持。定期監視も停止した。監督ログのKeyboardInterruptはユーザー指定の停止を表し、ファーム故障の判定ではない。

USBまとめ読みはこの試験開始前から製品ソース・通常候補UF2に入っていた。Pi RX offloadのENOBUFSはPi側の問題として切り分け済みで、最大速度測定用の受信設定対策とカーネルエラー監視を試験手順へ反映している。新しいファーム修正が未反映のまま耐久試験を開始した状態ではない。再開時は過去の部分記録を合算せず、選定した候補と条件で新しく連続24時間を測定する。
