# V102候補：USB送信投入の速度制限の分析

2026-10-21更新：同一の公開済みV102・負荷条件で**累積24時間を達成**した。最長連続22時間30分30秒、累積確認済み送受信は各方向約6,307万件、全監視エラー0。[集計範囲と終了監査](performance-V102-usb-bulk.md)。以下の中断・公開判断は当時の履歴であり、最新結果はリンク先を参照。

2026-10-20。750件/秒ずつの校正でPicoへの投入が途中約510件/秒にとどまった原因を分析した。耐久試験の非対称配分で回避する前に、入力経路の制限を切り分けるというユーザーの指示による。

## 結論

主因はファームがUSB入力を1文字ずつSDKへ要求していたこと。FD64バイトのSLCANコマンドは134文字あり、1コマンドで134回のSDK入力処理を呼ぶ。SDKの接続・残量検査、mutex取得、TinyUSB読出し等の固定費が文字数に比例して積み上がる。双方向時にはCAN受信表示のUSB出力も同じUSB mutexを使い、入力経路の追加負担となっていた。

同じホスト・USB接続で、読出しだけを最大64バイト単位へ変えると、対称750件/秒ずつを120秒維持できた。CAN送信枠の回収や1件ずつハードウェアへ渡す方式は変更していない。今回の750件/秒未達を、USB物理帯域やCAN送信待ちだけで説明する根拠はない。

## コード経路

`transfer_tty2can()` → `getchar_timeout_us(0)` → SDK `stdio_getchar_timeout_us()` の `char buf[1]` → `stdio_get_until(..., 1, ...)` → `stdio_usb_in_chars()`。

SDK側はデータの有無を調べ、`stdio_usb_mutex`を取ってTinyUSBから指定バイト数を読む。`stdio_usb_out_chars()`も同じmutexを取る。core0のSLCAN入力・受付応答と、core1のCAN受信表示がこの経路を共有する。

根拠：[SDK 2.2.0 stdio](https://github.com/raspberrypi/pico-sdk/blob/2.2.0/src/rp2_common/pico_stdio/stdio.c)、[SDK 2.2.0 stdio_usb](https://github.com/raspberrypi/pico-sdk/blob/2.2.0/src/rp2_common/pico_stdio_usb/stdio_usb.c)、本リポジトリの `slcan/slcan.c`。SDK原本は変更せず、計時用コピーだけを別ビルドで使用した。

## CAN処理を除いた比較

CANをCloseし、フレームを送らずに134文字入力とBEL応答だけを3,000回繰り返した。

| 条件 | 処理速度 |
| --- | ---: |
| 通常候補・ホストwrite-ready待ち | 782.5件/秒 |
| 通常候補・ホスト非ブロッキングpoll | 774.3件/秒 |
| 1文字読出し＋診断計時・poll | 726.0件/秒 |
| 最大64バイト読出し＋同じ診断計時・poll | 2,882.7件/秒 |

全ケースで3,000件BELと一致し、余計な応答は0。ホスト側の送信方法を変えた差は小さく、ファーム側の読出し変更で大幅に改善した。計時を追加すると性能が下がるため、診断版の絶対値を通常候補の速度と混同しない。

| 計時比較（402,002バイト、qコマンド2バイトを含む） | 1文字読出し | 最大64バイト読出し |
| --- | ---: | ---: |
| 正の入力read回数 | 402,002 | 6,283 |
| 1回当たりの平均バイト数 | 1.0 | 63.98 |
| 正のUSB入力処理の合計 | 2.794秒 | 0.117秒 |
| 1バイト当たり | 6.95µs | 0.291µs |

1文字版の134文字入力では、計時したUSB入力処理だけで約0.93msを使う。CAN処理・コマンド解析・ホスト待ち等は別に必要になる。

## 双方向で増える負担

各7,500件の短時間比較では、1文字版の入力mutex取得経路の合計時間は片方向0.995秒から双方向2.230秒へ増えた。core1のUSB出力処理は双方向時に1.319秒を使っていた。まとめ読み版では、同じ7,500件ずつの双方向通信で入力mutex経路は0.057秒となった。

この計時はmutex取得呼出しの経過時間であり、割り込み等も含む純粋なロック待ち時間の精密測定ではない。USB入力処理の合計時間とも重複するため、加算してCPU負荷率にしない。計時側の固定費もあるが、読出し方法だけを変えた比較と、診断なし版の再試験で因果を確認した。

## 診断なし修正候補の検証

修正はUSBから取る単位を最大64バイトにし、取り出した文字を従来と同じ順番で既存のコマンド組立てへ渡すもの。64バイトがたまるまで待たず、現時点である分だけを読む。未完成コマンドを保持する既存の静的バッファ、CR終端、入力超過時の処理は維持する。SDK、CANドライバ、FIFO容量・順序・再送方針を変更しない。

| 検証 | 結果 |
| --- | --- |
| 対称750件/秒・FD64B BRS 500k/2M・120秒 | 送受信各90,000件、内容・順序一致、要求ペース維持 |
| 不一致・BEL・ソケットdrop・不要な復旧 | 0 |
| 通常受信 | Classic/FD等52パターン成功 |
| 双方向 | 各1,000件、順序・内容一致 |
| 134文字コマンドの分割 | 全133分割位置で保持・再組立て成功 |
| 連結コマンド | 4件、順序・内容一致 |
| 256文字入力超過後の再同期 | 元のファームと応答バイト列が完全一致 |

最初の分割試験は、試験側が既存V応答の二重CRと、入力超過後の空コマンドに対するBELを期待値へ含めていなかった。CANの137件はその時点でも一致していた。期待値をコードで確認して修正し、元のファームと修正候補の両方で同じ試験をやり直し、応答列も一致することを確認した。最初の応答比較は未合格試行として採用しない。

修正候補は隔離したソースから通常ビルドし、診断・故障注入シンボルがないことを確認した。SHA-256: `f073740c23d2c449a529bcc27037a8723530d11662f99891fa866a034044cf85`。分析後、この最小差分を製品ソースへ反映した。製品ソースからの通常ビルドUF2も同じSHA-256となり、試験済み候補との一致を確認した。ビルド・差分・生ログと結果は試験記録へ保持している。[機械可読の要約](../tests/results/V102-usb-input.json)。

## 耐久試験への扱い

非対称450/1,000件毎秒のMini試験は、投入経路分析を優先する指示で27分の記録を保存して停止した。24時間完了として扱わない。非対称の旧耐久試験は中断したまま。原因分析と短時間検証後に入力の最小修正を製品ソースへ反映し、復旧6条件×10回の回帰も60/60成功した。修正後の性能再測定と対称負荷の校正が合格した場合だけ、新しい24時間試験へ進む。公開は検証後とする。

入力の最小修正と復旧回帰を確認したため、残る性能再測定・校正後に、対称730件/秒ずつ（フレーム時間モデルで合計約50.0%）の新しい連続24時間試験を行う。過去の中断試験は合算しない。Classic CANを選ぶ場合のユーザー指定は約70%。

## 追加性能回帰で見つかったPi受信側の制約

修正後の復旧60試行、通常候補の実bus-off復帰10試行、データ付き最大速度・遅延15試行は合格した。一方、公称1Mbps・DLC0の最短フレーム試験では、受付・送信完了件数に対してPi受信数が不足したため、全性能回帰の監査を未合格として停止した。この監査停止時点では新しい24時間試験へ進まなかった。その後の経過は末尾に記す。

末尾到着を300ms待つ再試験でも途中の連続フレームが欠けた。Piのカーネル受信パケット数はアプリ受信件数と一致し、ソケットdropは0。さらに専用の8試行で、Piの`/sys/class/net/rcan2/statistics/rx_fifo_errors`の増分を測った。

| 公称速度・形式 | 2回の不足数 | 2回のPi rx_fifo_errors増分 |
| --- | --- | --- |
| 500kbps Classic DLC0 | 0, 0 | 0, 0 |
| 500kbps FD BRS DLC0 | 0, 0 | 0, 0 |
| 1Mbps Classic DLC0 | 9, 10 | 9, 10 |
| 1Mbps FD BRS DLC0 | 3, 17 | 3, 17 |

不足はPi受信経路で記録されており、この試験だけを根拠にPicoの送信欠落とは判断しない。これは750件/秒のUSB入力制限とは別の問題である。Pi側カーネルは6.6.31+rpt-rpi-v8。公式Raspberry Pi Linuxの同系列`mcp251xfd-rx.c`では、この統計は古いRXタイムスタンプの検出時とRX offloadへのキュー投入失敗時に増えるため、カウンタ名だけで物理RX FIFO満杯や特定のエラッタが原因と断定できない。この時点ではどちらの経路か未確定だったため、最大速度の測定環境としてこの条件を合格扱いにせず、以下の直接観測を行った。

参照：[公式Raspberry Pi Linux mcp251xfd-rx.c](https://github.com/raspberrypi/linux/blob/rpi-6.6.y/drivers/net/can/spi/mcp251xfd/mcp251xfd-rx.c)。この参照は同系列のソースであり、実行中モジュールのビルド元との完全一致を確認したものではない。

### 受信キューの直接観測と測定環境の対策

Pi上に独立したtraceインスタンスと一時的なkretprobeを設け、`can_rx_offload_queue_timestamp()`の失敗戻り値だけを記録した。対象外ポートはDOWNのまま。他のtrace設定は変更していない。8試行で不足した38件に対して、対象SPI1.0 IRQ処理からの`-ENOBUFS`（-105）が38件記録され、`rx_fifo_errors`の増分も38件で一致した。今回の不足はPiのCAN RX offload受信キューへの投入失敗と特定できた。古いタイムスタンプを検出する別経路が原因だとする証拠はない。観測用イベント・インスタンスは削除し、元のtrace設定との一致を確認した。

rcan2だけのthreaded NAPI有効化では解消しなかった。続いて、rcan2だけで`ethtool -C rcan2 rx-usecs-irq 250 rx-frames-irq 1`を一時設定すると、ドライバが実際には250µs・8フレームへ調整した。この状態の比較8試行は受付数と受信数、全IDの順序が一致し、PiのFIFOエラー増分・ソケットdropとも0だった。設定後の読み戻し値を試験条件として記録し、終了時に元の0µs・1フレーム、RXリング20/TX4、threaded NAPI 0へ戻した。

この受信設定は最大速度測定にだけ使用し、修正後の48試行を同条件で再検証する。RTTにはPi側の受信設定の影響も含む。通常設定で先に合格したデータ付き15試行は別の記録として保持する。24時間耐久試験にはPiの通常受信設定を使い、対称730件/秒ずつの120秒校正後に開始する。耐久試験の各チェックポイントと最終結果には、ソケットdropに加えてPiのカーネル受信エラー5種類の増分が0であることも要求する。

## 24時間試験の開始

最大速度測定の48試行は、Pi受信設定250µs/8フレームで全件・形式・内容・順序の各判定に合格し、全試行を通したカーネル受信エラー増分も0だった。通常設定0µs/1フレームへ復元後、対称730件/秒ずつ・120秒の校正も各87,600件一致、全エラー0で合格した。2026-10-20 08:02:39 JSTから新しい連続24時間試験を開始した。終了予定は翌21日08:03頃。完了後の全件監査までは未完了とする。[修正後の性能と耐久試験](performance-V102-usb-bulk.md)。

## 対応の織り込み状況と途中停止

2026-10-20 09:32 JST、ユーザー指示で耐久試験を停止した。最終チェックポイントは1時間29分30.105秒、各方向約392万件で全監視エラー0。24時間完了として扱わない。停止・対象設定復元・定期監視停止を確認した。

| 発見事項 | 対応と反映先 | 状態 |
| --- | --- | --- |
| 1文字ずつのUSB入力処理で投入速度不足 | `slcan/slcan.c`で最大64バイト読出し | 製品ソース・今回の通常候補UF2へ反映済み、750件/秒ずつ120秒照合済み |
| PiのCAN RX offloadキュー投入時ENOBUFS | 最大速度測定時だけ対象rcan2へ受信割り込み250µs/8フレームを設定し、終了後は復元 | 比較8回と性能48回で全判定合格。Picoファームへ入れる修正ではなくPi側の測定条件 |
| ソケットdropだけではPi受信欠落を見逃す | `tests/hardware_soak.py`でカーネル受信エラー5種類の増分も判定 | 製品リポジトリの試験コードと今回のMini実行版へ反映済み |

製品ソース6ファイルのハッシュとUF2を試験開始時の証跡と再照合し、一致を確認した。これらの対応は既に織り込まれており、新しい未反映のPicoファーム修正はこの切り分けからは残っていない。2026-10-20、ユーザーの公開判断により、連続24時間試験の未完了を明記してV102を公開する。

## V102の公開について

2026-10-20、ユーザーの判断でV102を公開する。配布物は[通常ファーム pico-slcan-V102.uf2](../firmware/V102/pico-slcan-V102.uf2)で、USBまとめ読み候補とバイト列・SHA-256が一致する。診断・故障注入コードは含まない。連続24時間試験は途中停止・未完了のままであり、合格したとは扱わない。
