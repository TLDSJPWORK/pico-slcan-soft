# V102開発版：TX障害後の自動復旧

ソフトウェア版03の検証記録です。V101で確認したbus-off・SEQ異常後のFIFO停止、TEF overflow後の管理情報残留を修正します。

## 動作

- ISRでは原因を記録してTX完了割り込みを一時停止し、foregroundでTXだけを段階的にabort/resetします。
- ハードウェアTXキューとTEFのreset完了・空き状態を確認してから、参照配列と空き枠数を初期化します。
- 受信ソフトFIFO・受信フィルタ・ビットタイミングは再初期化しません。
- 完了が確認できた先頭はFIFOから取り出します。未確認の先頭は保持し、自動で再送します。
- ACK待ちだけでは打ち切りません。TXREQが消えたのに完了がない状態は、後のhealth pollで再確認してから復旧します。
- 投入失敗の再試行と復旧は1ms以上の間隔で進め、USBコマンド処理を止めません。

## 配達済みか不明な場合

完了イベントの喪失は、CANバス上の配達失敗とは限りません。本実装はデータを残して再送するため、障害復帰時は重複があり得ます。SEQ破損試験でも実際に重複を確認しました。受信アプリケーションで重複排除が必要なら、連番等をデータへ含めてください。

`w`の`uncertain`は、この判断をした回数です。重複したフレーム数そのものではありません。`recoveries`は復旧成功回数、`faults`は最後の原因、`pending`は現在の復旧待ち原因（1=bus-off、2=SEQ、4=TEF、8=管理不一致）です。CRは引き続きFIFO受付を意味し、配達完了ではありません。

## 実機試験

RP2040 pico-slcanとLinux SocketCANのMCP2518FDを接続して2026-10-19に検証しました。通常通信は公称500k、FDデータ2M。bus-off試験では公称125k/データ2Mの対向サンプル点を意図的に不一致にして障害を発生させ、対向設定だけを整合させてC/Oなしの再開を確認します。設定不一致による初発エラーをファームの不具合として扱う試験ではありません。

最終結果は[機械可読の結果](../tests/results/V102.json)に記録しました。試験で再起動するのはファーム書換え対象のPicoだけで、対向Linuxは再起動しません。操作するCANポートも指定の1ポートだけです。

| FIFO満杯で管理情報破損／TEF overflow | 各1回成功、各1,000件を順序どおり受信 |
| SEQ破損中の双方向通信 | 1回成功、送信の固有連番1,000件、重複1件を含む1,001件のecho受信が完全一致 |

診断版の6条件×10回は全60回成功し、最終的にドライバの空き枠20、参照残留0、TEF空・overflow解除を確認しました。TEF overflow試験は、診断専用コードで通常の「1件ずつ投入」を迂回し、20件をハードウェアへ投入して容量12のTEFを実際にあふれさせています。通常運転で自然発生したという主張ではありません。

SEQ破損試験では各回1件の重複を観測しました。満杯状態のTEF試験でも1件、双方向SEQ試験でも1件の重複を観測しています。未確認フレームを保持する設計のため、これらは上記の配達意味論どおりです。

125k/2Mで対向の公称サンプル点75%は成功、80%は停止した比較は、設定不一致による通信不能として扱います。今回の修正対象は、その障害を除去した後もFIFOが再開しない問題です。

試験終了時は製品候補V0103を実機へ書き込み、CANを閉じ、対向ポートを元のDOWN状態に戻しました。他ポート操作・Pi再起動・システム全体の受信バッファ変更は行っていません。本記録は障害復旧の検証です。速度・遅延の測定と投入経路の分析のため中断したMiniの24時間試験は[性能レポート](performance-V102.md)へ分けて記録しています。

## 再実行用診断ビルド

診断用コードは別ディレクトリへ生成し、製品ソースと配布候補UF2には故障注入コマンドを含めません。

```sh
python3 tests/prepare_recovery_diagnostics.py /tmp/pico-recovery-diagnostics
cmake -S /tmp/pico-recovery-diagnostics -B /tmp/pico-recovery-build -G Ninja \
  -DPICO_SDK_PATH=/path/to/pico-sdk -DPICO_BOARD=pico
cmake --build /tmp/pico-recovery-build
```

生成した診断ファームを専用試験機へ書き込んでから実行します。指定ポートのDOWN/UP、送信管理情報の破損、TEF overflowを含むため、専用試験バスで使用してください。Linux側には`ip`と受信ソケットのための`sudo -n`権限が必要です。`SO_RCVBUFFORCE`による受信バッファ変更は当該ソケットだけで、システム全体のsysctlは変更しません。

```sh
SERIAL_PORT=/dev/ttyACM0 CAN_IF=can0 REPEAT=10 \
  python3 tests/hardware_recovery.py output/recovery
```

USBとSocketCANを別マシンに接続する場合は`SSH_TARGET=user@can-test-host`を追加します。既存のSSH接続を使う場合は`SSH_CONTROL_PATH`も指定できます。すでにrootのLinux環境では`SUDO=''`を指定できます。

製品候補の通常受信・同時送受信・満杯試験には、既存の`hardware_rx_duplex.py`と`hardware_burst.py`を使用します。試験後は診断用ファームを製品候補へ置き換えてください。

## USB入力改善後の候補

1文字ずつのUSB読出しが750件/秒の投入を制限していたため、最大64バイトのまとめ読出しへ変更した。詳細は[USB入力分析](usb-input-analysis-V102.md)。修正後の製品ソースから作った[通常UF2候補](../firmware/V102/pico-slcan-V102-usb-bulk-candidate.uf2)のSHA-256は `f073740c23d2c449a529bcc27037a8723530d11662f99891fa866a034044cf85`。上の旧候補とは別の成果物として保持する。

この入力変更後の診断版でも、復旧6条件×10回は60/60成功し、空き枠20・参照残留0・TEF空・overflow解除を再確認した。通常候補の実bus-off・性能再測定・対称負荷の校正を順次実施し、合格後に24時間試験へ進む。この段階では公開前の検証だった。現在の配布物はREADMEを参照。

### USBまとめ読み修正後の性能回帰と新しい耐久試験

2026-10-20、通常候補 f073740c23d2c449a529bcc27037a8723530d11662f99891fa866a034044cf85 の派生診断で復旧60/60、通常候補の実bus-off復帰10/10を確認した。性能回帰48/48も合格。1Mbps DLC0のPi受信キュー溢れは直接観測で切り分け、最大速度測定に限りPi受信割り込み250µs/8フレームを使用した。元の設定へ戻した対称120秒校正は各87,600件一致、エラー0。08:02:39 JSTから対称730件/秒ずつの24時間試験を開始した。まだ完了結果ではない。[測定値と条件](performance-V102-usb-bulk.md)。

2026-10-20 09:32 JST、ユーザー指示で上記耐久試験を途中停止。最終チェックポイント1時間29分30.105秒・各方向約392万件で監視エラー0。24時間未完了。通常候補・対象CAN設定の復元と監視停止を確認した。USB修正とPi側の観測・測定条件対策は製品ソース／試験手順へ反映済み。

## V102の公開について

2026-10-20、ユーザーの判断でV102を公開する。配布物は[通常ファーム pico-slcan-V102.uf2](../firmware/V102/pico-slcan-V102.uf2)で、USBまとめ読み候補とバイト列・SHA-256が一致する。診断・故障注入コードは含まない。連続24時間試験は途中停止・未完了のままであり、合格したとは扱わない。
