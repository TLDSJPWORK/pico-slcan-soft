# V102候補：送信速度・遅延と連続運転試験

USB入力修正後の最新測定と対称24時間試験は[10/20の記録](performance-V102-usb-bulk.md)を参照。この文書の速度表はUSB入力修正前の候補の記録。

2026-10-19測定。復旧方針である障害時の再送・重複は残不具合に数えません。今回の通常通信試験では意図的な障害注入は行っていません。

## 条件と判定

RP2040 pico-slcanとMCP2518FD SocketCANを接続。通常候補UF2のSHA-256は `fbdb2ea3e22abb415bb7e49c27e2fceb880bb472bd11031db3d8e3e70b036d5a`。MacのUSBシリアルから入力し、対向Linuxで受信しました。Piの公称サンプル点80%、SJWは125k/500kで8、1Mで4。FDデータ2M・サンプル点80%・SJW2。125k条件はClassicです。

各条件3回。受信側はハードウェア時刻を使用し、当該ソケットのみ受信バッファを拡大しました。採用した全試行でハードウェア時刻あり・ソケットdrop 0を確認しています。連番またはID列と内容を照合し、CRで受け付けた列が実際に同じ順で届くことを判定しました。

## 読み取り方と限界

FD64BのUSB入力込み実効速度は、FIFO内から供給した速度より低く、今回のMac→USB→SLCAN入力が供給を制限しています。1件送信方式にも完了確認・SPI・foreground処理の間隔があるため、物理CANの理論帯域を使い切る方式ではありません。表はこの配線・データ列・ホスト構成で測った能力です。全条件の絶対最大値やリアルタイム保証ではありません。

ACKが戻らない間は保持を続ける仕様なので、障害やACK停止を含む送信遅延に有限の上限はありません。FIFO満杯時はBELです。波形測定によるビット位置・遅延の検証は行っていません。

1M設定の初回でPiにSJW8を指定し、ドライバが設定を拒否した試行は不採用です。SJW4へ修正して未完了の条件から再開しました。通信失敗やファーム停止としては扱っていません。

## 連続運転試験（ユーザーの指示で保留）

通常候補UF2へ検証付きで戻し、公称500k／データ2M・FD64B・BRSあり、双方向各200件/秒で2026-10-19 18:48 JSTに開始しました。MacBook Proを試験環境から離して使用するため、ユーザーの指示で同日20:51 JSTに停止しました。

最後の完全なチェックポイントは **2時間3分0.18秒**。Mac→Piは1,476,037件、Pi→Macは1,476,038件を確認し、連番・内容不一致、BEL、対向送信エラー、ソケットdrop、不要な復旧はすべて0でした。方向ごとのチェック時刻は同時ではないため、進行中の件数差は欠落・重複を意味しません。停止時点までの全件を排出して照合した最終結果ではなく、保存したチェックポイントの結果です。

**この中断時点では24時間未完了・公開保留でした。現在のV102は未完了を明記して公開します。** この約2時間の結果を24時間の成功として扱いません。再開可能になったら別の結果ディレクトリで連続24時間を最初から測定し、今回の部分記録は保持します。予定は各方向17,280,000件です。

停止時にCANをCloseし、対象ポートは元の公称125k／データ2M・サンプル点80%の設定とDOWN状態へ戻しました。Piのboot ID不変と他CANポートのDOWNを確認しました。Macの試験用スリープ抑止は終了し、定期確認も停止しています。現在の試験構成はLAN/SSHを使うため、次回の実行中もLAN接続が必要です。

## Miniでの24時間試験：FDバス負荷約50%（投入経路の分析のため中断）

2026-10-20 06:51 JSTにMac mini上で新しい連続24時間試験を開始しました。ユーザーの指示で投入経路の分析を先に行うため、同日07:18 JSTに中断しました。最後のチェックポイントは27分0.04秒、送信729,016件・受信1,620,020件で、不一致・BEL・drop・不要な復旧は0です。最終排出まで照合した24時間完了結果ではありません。候補UF2のフラッシュ内容を転送ファイルと照合し、同一であることを確認してから開始しました。Miniの独立プロセスで記録を残すため、MacBook ProのSSH切断・スリープには依存しません。MiniとPi間のLAN、USBとCAN接続は維持します。

ユーザーの指定に合わせ、FDの合計バス負荷を約50%へ引き上げました。Classic CANで実行する場合の指定は約70%です。今回の24時間はFD64バイト・BRSあり、公称500k／データ2Mです。

| 方向 | 目標件/秒 | 推定バス占有率 | 24時間の予定件数 |
| --- | ---: | ---: | ---: |
| Pico → Pi | 450 | 約15.4% | 38,880,000 |
| Pi → Pico | 1,000 | 約34.3% | 86,400,000 |
| 同じCANバスの合計 | 1,450 | **約49.7%** | 125,280,000 |

標準ID 0x621/0x622と実際の64バイトのデータ列を使い、動的スタッフビット、CRCの固定スタッフビット、BRS/CRC delimiterでの速度切替、ACK/EOF、3ビットのintermissionを含めたフレーム時間モデルによる推定です。65,536連番の標本平均は約342.5µs/フレームでした。再現コードは `tests/canfd_load_model.py`。フィールド長は[Linux CANフレーム長定義](https://github.com/torvalds/linux/blob/master/include/linux/can/length.h)と照合しています。波形で実測したバス負荷ではなく、伝搬・再同期・実タイミングの差もあるため、小数点以下を保証する値ではありません。

Piの既存`canbusload`はFD非対応で0%を表示したため採用していません。現行[can-utilsのフレーム長計算](https://github.com/linux-can/can-utils/blob/master/canframelen.c)にもFDのexact計算未対応が明記されているため、ツールの概算表示を実測値とは扱いません。

750件/秒ずつの最初の校正は、全45,000件ずつの照合には成功しましたがUSB送信が要求ペースに追いつかず、60秒分の排出に約85秒かかりました。50%負荷を維持した試験としては不採用です。450/1,000件毎秒の120秒校正では、54,000件送信・120,000件受信が一致し、各チェックポイントで要求ペースを維持、不一致・BEL・drop・不要な復旧は0でした。方向別の配分を明示してこの条件を採用しています。

24時間の本試験では、件数・連番・内容・受付応答・drop・FIFO・復旧数に加えて、ホストと対向の送信ペースの遅れも判定します。**本試験は中断・未完了です。V102は未完了を明記して公開します。** USB投入速度の原因分析と最小修正候補の実機比較は[入力経路の分析](usb-input-analysis-V102.md)を参照してください。耐久試験の再開前に、修正候補の回帰を確認します。 前回Proで保存した2時間3分を今回の24時間へ合算しません。
