# pico-slcan firmware

JP WORKS pico-slcan（RP2040 + MCP251xFD）用のUSB SLCAN / CAN FDファームウェアです。

## V102（ソフトウェア版03）

USB入力を最大64バイトずつ読む方式へ変更し、1文字ずつの読出しが送信投入速度を制限する問題も修正しました。双方向750件/秒を120秒、各90,000件の内容・順序一致で確認しています。

復旧60試行、通常ファームの実bus-off復帰10試行、速度・遅延48試行は合格しました。耐久試験は2026-10-21に**累積24時間**を達成しました。最長連続22時間30分30秒、累積確認済み送受信は各方向約6,307万件で、全監視エラー0でした。中断区間の確認済み実績を加算した結果であり、連続24時間の完走結果ではありません。

bus-off、送信完了SEQの異常、TEFオーバーフロー、TX管理情報の不一致を検出すると、受付済みのFIFOを保持してTXだけを自動復旧します。CANのClose/Openやホスト側の再接続は不要です。受信FIFO・受信フィルタ・ビットタイミングは再初期化しません。正常なACK待ちは打ち切りません。

配達済みか確認できない先頭フレームも保持して再送するため、障害復帰時は同じフレームが重複して届くことがあります。CAN上の重複を許容できないアプリケーションでは、データに連番を付ける等で受信側も判定してください。受付成功CRは配達完了を意味しません。

`w`の末尾に以下の状態を追加します。カウンタは電源投入後の累積です。

| 項目 | 意味 |
|---|---|
| `recoveries` | TX管理情報の自動復旧が完了した回数 |
| `uncertain` | 配達確認のない先頭を保持して再送する判断をした回数。実際の重複数ではありません |
| `faults` | 最後に復旧した原因のビットマスク：1=bus-off、2=SEQ、4=TEF overflow、8=管理不一致 |
| `pending` | 復旧待ちの原因ビットマスク。0なら復旧待ちなし |

投入失敗の再試行と復旧処理は1ms以上の間隔で行います。復旧処理は段階的に進め、ハードウェアのabort/reset完了を待つ間もUSBコマンド処理を続けます。`C`は従来どおり待ちデータの明示取消です。

復旧試験の手順と結果は[V102の検証](docs/validation-V102.md)、修正後の速度・遅延と対称24時間試験は[最新の性能レポート](docs/performance-V102-usb-bulk.md)（累積24時間達成・連続最長22時間30分30秒）、750件/秒の投入制限の原因は[USB入力分析](docs/usb-input-analysis-V102.md)を参照してください。USB入力修正前の測定は[10/19の記録](docs/performance-V102.md)に保持しています。

## V101

USBからCANの送信能力を超えるバーストを入力したときに、送信できなかったフレームへ成功応答を返す問題を修正しました。1,000件の送信FIFOでバーストを保持し、送信完了に応じて順番に送り出します。

- FIFOへ受け付けたとき：CR（`0x0D`）。CANバス上の送信完了とは異なります。
- FIFO満杯またはCAN Close中：BEL（`0x07`）。FIFO内の既存データは上書きしません。
- 1,000件にはコントローラで送信中の先頭1件も含みます。1件76バイト、FIFO合計76,000バイトです。
- ACKがない間も受付済みのデータを保持します。ACKが復帰すると続けて送信します。
- `C`はCANを停止し、送信待ちを取り消します。`O`で再開できます。

入力がCANの送信能力を継続的に超える場合は、1,000件でも満杯になります。ホストはBELを扱い、送信ペースを制御してください。順序維持のためハードウェアへは1件ずつ渡します。最大スループットや遅延上限の測定結果ではありません。

V101ではFD受信時のデータコピー、拡張IDの受信表示、TX管理配列の初期化、RX FIFOサイズ設定、CAN割り込みと別コアの受信処理の排他も修正しています。

## ダウンロードと更新

[pico-slcan-V102.uf2](https://github.com/TLDSJPWORK/pico-slcan-soft/raw/refs/heads/main/firmware/V102/pico-slcan-V102.uf2)をダウンロードしてください。[SHA-256](firmware/V102/SHA256SUMS)も確認できます。過去の[V101リリース](https://github.com/TLDSJPWORK/pico-slcan-soft/releases/tag/V101)も保持しています。

1. ホスト側のCAN通信を停止します。
2. PicoのBOOTSELを押しながらUSB接続します。
3. `RPI-RP2` ドライブへUF2をコピーします。
4. 再起動後、USBシリアルから `V\r` でバージョンを確認します。下位2桁がソフトウェア版の `03` です。上位2桁は基板のGPIO設定に依存します。試験機では `V0103` でした。

配布UF2は本リポジトリの `PICO_BOARD=pico` 向けです。異なるSPI配線やCANコントローラの発振子を持つ基板には、そのまま適用しないでください。

## コマンド例

USBシリアルでは各コマンドをCRで終端します。

```text
C       CAN停止・待ちデータ取消
S6      公称500 kbit/s（停止中に設定）
Y2      FDデータ2 Mbit/s（停止中に設定）
O       CAN開始
V       バージョン
N       シリアル番号
w       TX FIFO状態
```

送信は `t/T`（標準/拡張CAN）、`r/R`（RTR）、`d/D`（FD・BRSなし）、`b/B`（FD・BRSあり）に対応します。例：`t1238AABBCCDDEEFF0011\r`。

`w\r` は `W accepted=... rejected=... completed=... queued=... capacity=1000 high_water=... retries=... inflight=...\r` を返します。`queued`は送信中を含む現在の待ち件数です。各カウンタは起動後の累積で、`C`による待ちデータの取消を成功件数から差し引きません。`retries`はコントローラへの投入を拒否された回数で、ACK待ちによるCANハードウェアの再送回数ではありません。

## ビルド

Pico SDK 2.2.0、Arm GNU Toolchain 14.2系、CMake、Ninjaでビルドを確認しています。

```sh
cmake -S . -B build -G Ninja \
  -DPICO_SDK_PATH=/path/to/pico-sdk \
  -DPICO_BOARD=pico
cmake --build build
```

SDKに必要なpicotoolがある場合、`build/pico-slcan.uf2`が生成されます。ELFから変換する場合：

```sh
picotool uf2 convert build/pico-slcan.elf pico-slcan.uf2
```

## 検証

[V101の実機検証記録](docs/validation-V101.md)と[機械可読の結果](tests/results/V101.json)を参照してください。受信52パターン、FD64バイトの各方向1,000件同時送受信、バースト、満杯時エラー、ACK復帰を公開するUF2で照合しています。

試験プログラムはPython標準ライブラリのみを使います。LinuxでPicoとSocketCAN対向を同じマシンへ接続するか、`SSH_TARGET`で対向Linuxを指定できます。試験条件と実行例は検証記録を参照してください。
